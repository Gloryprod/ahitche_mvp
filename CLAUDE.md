# CLAUDE.md

## Contexte Ahitché
- Service d'approvisionnement et de livraison alimentaire à domicile, à Cotonou et Abomey-Calavi (Bénin).
- Trois packs publics : **AHI Essentiel**, **AHI Équilibré** et **AHI Confort**, avec des prix en FCFA. Les packs AHI Réserve et AHI Fraîcheur existent aussi en base (`back/src/scripts/createFormules.js`).
- Le public est surtout sur mobile, avec des connexions parfois lentes. Il faut privilégier le poids léger, le lazy-loading et peu de requêtes bloquantes.
- Tout le site et tous les messages destinés aux utilisateurs sont en **français**.
- Respecter la charte graphique (couleurs, typo, logo). Les tokens se trouvent dans `front/src/assets/main.css` (`@theme`) :
  - Couleurs : `foret #1A5C38`, `savane #2E7D4F`, `or #F2B705`, `or-deep #D4A003`, `creme #F8F5EF`, `creme2 #F0EBE1`, `noir #111111`, `gris #4A5568`, `gris-lt #9AA5B4`.
  - Hors charte, choisies par le porteur pour les cartes des formules : `marine #1C2E4A` (en-tête d'AHI Confort) et `COULEURS_NIVEAU` (jauge « niveau de confort », `config/formules.ts`).
  - Polices : `font-display` = Fraunces (titres), `font-body` = Plus Jakarta Sans (texte).
  - Utiliser ces classes Tailwind (`bg-foret`, `text-or`…) plutôt que `gray-*`, `emerald-*` ou des hex en dur.

## Stack
- `front/` : Vue 3 + TypeScript, Vite 8, Tailwind CSS 4 (`@tailwindcss/vite`), vue-router, Pinia, TanStack Query (admin), vue-toastification, sweetalert2, jsPDF.
- `back/` : Node.js + Express 5 (CommonJS), MongoDB Atlas via Mongoose, JWT dans un cookie HttpOnly, Resend (e-mails), Cloudinary + multer (uploads).
- Production : front sur `https://ahitchebj.com`, API sur `https://api.ahitchebj.com`. En dev, Vite proxifie `/api` vers `http://localhost:5000`.
- Déploiement : le front est sur le compte Vercel gratuit (Hobby) de Gloryprod et le dépôt est privé, donc Vercel ne déploie que les commits dont l'auteur est Gloryprod. `main` n'avance que par une Pull Request fusionnée par Gloryprod avec « Create a merge commit » (pas « Squash » ni « Rebase », qui gardent l'auteur des commits) ; jamais de push direct sur `main`. L'API (Render) n'a pas cette limite.

## Commandes
```bash
# Front (dans front/)
npm run dev          # serveur Vite
npm run build        # type-check + build
npm run lint         # oxlint + eslint (--fix)
npm run test:unit    # vitest
npm run test:e2e     # playwright

# Back (dans back/)
npm run dev          # node --watch index.js (relance à chaque modification)
npm start
node src/scripts/createAdmin.js     # crée l'admin (ADMIN_PASSWORD dans .env)
node src/scripts/createFormules.js  # upsert des formules (prix, « Bientôt » ; cycle de relance seulement à la création, ensuite réglé dans l'admin)
node src/scripts/migrerDonnees.js   # migration idempotente (téléphone, fournisseurs, zones, statuts, taux, admin principal)
STAFF_PASSWORD=… node src/scripts/createStaff.js <email> "<Nom>" <role> [--livreur "<fiche livreur>"]  # compte de l'équipe
STAFF_PASSWORD=… node src/scripts/importerDonnees.js ../docs-internes/imports [--appliquer] [--attendu <json>]  # import 01 à 11 (simulation sans --appliquer)
node src/scripts/decisionsMiseEnService.js ../docs-internes/imports [--appliquer]  # décisions du porteur après l'import (prix admin, anciens lots et règles, commandes d'essai, compte admin générique)
node src/scripts/controlerDonnees.js [--attendu <json>]  # contrôles B.4, lecture seule
MONGO_URI=<lecture seule> node src/scripts/inventaireBase.js  # inventaire d'une base (nombres seulement, aucune donnée personnelle)
MONGO_URI=<lecture seule> node src/scripts/sauvegarderBase.js [dossier]  # sauvegarde complète (défaut : ../docs-internes/sauvegardes)
MONGO_URI=<base vide> node src/scripts/restaurerBase.js <dossier>       # restauration, refusée si la base n'est pas vide
MONGO_URI=… node src/scripts/archiverDonneesTest.js <03_produits.csv> [--garder REF,…] [--archiver-produits REF,…] [--appliquer [--forcer]]  # archive les données de test (bons, lots, mouvements, dépenses prévues de ces lots, produits hors référentiel) ; simulation par défaut ; --forcer exigé si des bons au format facture existent : jamais après les premières saisies réelles
node src/scripts/saisirFacture.js <catalogue|facture|transformation|controle> <fichier.json> [--api <url>] [--lignes <07_budget_lignes.csv>] [--appliquer]  # saisie des achats par l'API de l'admin (compte admin demandé dans le terminal, simulation par défaut ; fiches dans docs-internes/achats/)
```
Sauvegarde automatique : `.github/workflows/sauvegarde-hebdomadaire.yml` (dimanche, chiffrée, 35 jours), active dès que les secrets GitHub `SAUVEGARDE_MONGO_URI` et `SAUVEGARDE_PHRASE` existent. Surveillance : `GET /api/sante` (200 si l'API et la base répondent, 503 sinon).
L'import ne touche jamais la production sans `--appliquer` : la simulation s'exécute dans une transaction annulée et affiche les écarts. Ordre de mise en service : sauvegarde, migrerDonnees, createFormules, import, decisionsMiseEnService, controlerDonnees ; à répéter d'abord sur la base de recette `ahitche_recette` (la production est la base `test` du cluster Atlas). Atlas annule toute transaction de plus de 60 s : les scripts chargent chaque liste une fois par étape au lieu d'une requête par ligne. Les fichiers CSV et les valeurs attendues des contrôles restent dans `docs-internes/` (exclu de Git).
Les transactions MongoDB (livraison + sortie de stock FIFO) exigent un replica set : c'est le cas sur Atlas ; en local, utiliser `MongoMemoryReplSet` ou un replica set à un nœud.
Variables d'environnement du back : `MONGO_URI`, `JWT_SECRET`, `RESEND_API_KEY`, `FRONTEND_URL`, `CLOUDINARY_*`, `ADMIN_PASSWORD`, `NODE_ENV`, `PORT`, `INACTIVITE_MINUTES` (facultative, 60 par défaut : déconnexion de l'équipe après inactivité), `TRUST_PROXY` (1 derrière l'hébergeur : vraie adresse IP pour les limites) et `SENTRY_DSN` (facultative : suivi des erreurs, `back/instrument.js`, sans donnée personnelle).

## Structure
- `front/src/views/` : pages (accueil, login, register, reset, blog et page d'un contenu `/blog/:slug`, dashboards user et admin). Liste des pages : `router/routes.ts` (partagée par le routeur et le rendu au build).
- Référencement : `services/referencement.ts` (canonique et noindex par page, aperçu de partage d'un article, données structurées GroceryStore, FAQPage, Article). Le haut de l'accueil (menu et titre, la page entière coûtait trop sur téléphone) est rendu en HTML au build (`npm run build` lance `postbuild` : `vite.prerendu.config.ts`, `src/entry-prerendu.ts`, `scripts/prerendre.mjs`) ; `dist/index.html` = accueil avec son haut rendu, `dist/app.html` = coquille des autres pages, `dist/404.html` = adresses inconnues (statut 404), voir `vercel.json`. Plan du site : `GET /api/public/sitemap.xml`, servi sur `/sitemap.xml`. L'API publique ne renvoie jamais les brouillons.
- `front/src/components/sections/` : sections de la page d'accueil (Hero, Formules, Comment ça marche…).
- `front/src/components/admin/` : back-office (commandes, stock, produits, formules, posts) et les sections Gestion : `prestataires/`, `logistique/`, `finances/`, `simulateurs/`, `nutrition/` (chargées à la demande).
- `front/src/components/client/` : blocs de l'espace client (suivi alimentaire).
- Mesure d'audience sans cookie : `services/mesure.ts` (pages publiques vues, clics vers WhatsApp avec leur origine : `data-mesure` du lien, sinon la section) envoie à `POST /api/public/mesure`, qui ajoute 1 au total du jour (modèle `Mesure` : ni IP, ni identifiant, robots et navigateurs automatisés ignorés). Résumé : `GET /api/admin/mesures` (section `mesures`), carte « Fréquentation du site » du tableau de bord. Expliquée dans les Mentions légales.
- Compléments de la semaine (section « Disponible cette semaine » de l'accueil) : produits « extra » du catalogue cochés `cetteSemaine`, avec `photo` (Cloudinary, dossier `complements`) et `description`. Gérés dans `components/admin/complements/` (section `complements` : admin et gestionnaires ; suppression du catalogue réservée à l'admin), servis par `GET /api/public/complements` (nom, prix, unité, description, photo seulement). Un seul prix : celui du catalogue, appliqué aussi aux extras des commandes. Carte commune : `components/complements/CarteComplement.vue` ; photos réduites dans le navigateur avant l'envoi (`services/images.ts`).
- Avis clients : rédigés dans l'espace client (`components/client/MonAvis.vue`, `GET/PUT/DELETE /api/auth/avis`, un par client, comptes clients seulement, accord de publication obligatoire), publiés ou refusés avec un motif visible du client par l'admin (section `avis` : lecture admin et coordinateur, décision admin, journalisée ; `components/admin/avis/`), servis par `GET /api/public/avis` (prénom, quartier, note, texte) et affichés avant les témoignages de `config/temoignages.ts`, chargés à l'approche de la section. Le texte ne se modifie pas côté admin ; toute modification par le client le renvoie « À valider » et le retire du site.
- Contenus de l'accueil, à modifier dans `front/src/config/` sans toucher aux composants : `contact.ts` (WhatsApp, messages pré-remplis, Facebook, TikTok, horaires, délai de livraison), `formules.ts` (vitrine, prix, taille de foyer, couleur `teinte` et `niveau` de confort de chaque carte, produits de base et réglages de leur animation `ANIMATION_PRODUITS` : effet, durée, produits par groupe), `photos.ts` (emplacements « PHOTO À FOURNIR » : n'y mettre que des photos à licence vérifiable), `temoignages.ts` (avis réels validés par les clients uniquement), `faq.ts`, `actualites.ts`.
- `front/src/config/roles.ts` et `back/src/config/roles.js` : rôles (`user`, `admin`, `gestionnaire`, `comptable`, `nutritionniste`, `coordinateur`, `auditeur`) et droits lecture/écriture par section, à garder synchronisés. Le serveur fait foi (middleware `acces()`). Les gestionnaires n'ont accès ni aux marges ni aux finances (D-17) ; un gestionnaire relié à une fiche livreur (`User.livreurId`) ne voit que ses commandes, celles à planifier et leurs clients (`services/perimetreService.js`).
- `back/src/config/convention.js` : période de la convention N°171 (mois du projet du 26 au 25), sources de financement, pièces exigées par catégorie. Jamais de montant du budget dans le code.
- `front/src/config/commandes.ts` et `back/src/services/commandeService.js` : statuts de commande et passages autorisés.
- `front/src/stores/auth.ts` : état d'authentification (composable, pas un store Pinia ; `user`, `role`… sont des refs/computed, donc à lire avec `.value`). `stores/api.ts` : instance axios avec un intercepteur 401.
- `back/src/routes/` : `auth.js` (client), `admin.js` (back-office, droits par section), `public.js` (blog, zones).
- `back/src/controllers/`, `models/`, `services/` : logique Express et Mongoose. `services/compositionService.js` calcule la composition d'un pack (Formules, Logistique, Simulateurs).
- `back/src/data/zones-livraison.json` : 22 zones (arrondissements de Cotonou et d'Abomey-Calavi) et leurs quartiers.
- `docs/conception-menu-admin.md` : décisions métier du back-office (statuts, paiement, relances, rôles, APDP).

## Conventions
- Le code, les commentaires et les messages sont en français. On garde le style existant (`async function` + `module.exports` côté back, `<script setup lang="ts">` côté front).
- La commande se fait principalement par WhatsApp (`wa.me/22998136635`) avec un message pré-rempli.
- Les prix publics figurent aussi dans `front/public/llms.txt` (résumé pour les assistants IA) : à tenir à jour avec la vitrine.
- Les prix des packs sont définis à deux endroits : dans `front/src/config/formules.ts` (vitrine : cartes et prix d'appel du hero) et en base (`Formule`, référentiel dans `back/src/scripts/createFormules.js`). Toute modification de prix doit être faite aux deux endroits.
- Prix de vente = `prixCommercial` s'il est fixé par l'admin, sinon `prixActuel`. `GET /api/admin/formulas/:pack` est en lecture seule et renvoie la valeur issue du catalogue dans `prixCalcule`.
- Une commande client est enregistrée par le serveur, qui fixe lui-même le prix et la référence `CMD-xxx` (`orderReferenceService`). Les packs `bientotDisponible` (Réserve, Fraîcheur) sont visibles mais ne peuvent pas être commandés.
- Liste commune : 17 produits de base. L'Essentiel exclut l'huile de palme. Les quantités par pack ne sont pas affichées.
- Familles de produits (`Product.type`) : P « base fixe » (packs), V « extra » (vendus à la demande), MP « matière première » (transformée, ex. maïs → farine) et EMB « fourniture » (emballages). MP et EMB ne se vendent jamais : refusés dans une commande, hors packs, jamais affichés sur le site. Un type inconnu est refusé ; sans type, une modification garde le type existant.
- Commande : En attente → Confirmée → En préparation → En livraison → Livrée (paiement à la livraison : Mobile Money, référence obligatoire, ou espèces avec note, D-06 ; l'acompte ne reste que sur les anciennes commandes) ou Échec ; Annulée. Le serveur impose le prix (formule + extras au prix du catalogue − remise validée par l'admin, motif obligatoire). La compensation automatique « livraison > 24 h » est retirée (D-07, D-08) : la garantie est le remplacement d'un produit manquant ou abîmé à la livraison suivante.
- Site : packs mensuels depuis le 15/10/2026 (Essentiel, Équilibré, Confort : un pack couvre un mois, prix, repas et heures annoncés par mois, cycle 30 jours ; Fraîcheur 7 ; le cycle de relance se règle dans l'écran Formules de l'admin, `PATCH /api/admin/formulas/:pack/cycle`, 1 à 365 jours, journalisé, sans effet sur les textes du site), sans prix par jour ; prix barré = « valeur estimée » (matières du catalogue × coefficient, servie par `GET /api/public/formules/valeurs`, rien de barré si une valeur manque, D-03) ; livraison « à jour fixe » (`JOURS_LIVRAISON` dans `config/contact.ts`, vide tant que les jours ne sont pas confirmés) ; garantie : produit manquant ou abîmé remplacé à l'identique à la livraison suivante.
- Finances : toute action sur les dépenses, lignes budgétaires, taux, paramètres, prix et cycle de formule, produits, règles, lots et fiches prestataires passe par `journaliser()` (journal des modifications). Une dépense payée (justificatif obligatoire) ne se modifie plus. « Valide pour l'audit » se coche seul quand les pièces exigées par la catégorie de la ligne sont jointes. Un mois du projet clos ne se modifie plus sans réouverture par l'admin (motif tracé). Dépassement de ligne et paiement hors période : alerte sans blocage (D-20).
- Stock : un lot « à compter » garde quantité et prix vides jusqu'au comptage ; une entrée se rattache à la dépense de sa pièce, sans en créer une seconde ; la quantité ne change que par comptage ou correction motivée ; transformation (lot « Production interne ») et essai sont des mouvements à part ; le coût d'une sortie suit la valeur facturée du lot (au prorata).
- Achats : un bon au format facture porte la référence du BC signé (ou « Achat direct – facture n° … »), sa date (ou celle de la facture), le numéro de facture et les lignes de la facture (produit et quantité dans l'unité du produit) ; une facture = un bon actif ; un bon supprimé libère son numéro. « Réceptionner » (`POST /api/admin/bons-commande/:id/reception`, transaction) crée un lot par ligne (valeur = montant de la ligne, prix = montant ÷ quantité ; quantité reçue jamais au-delà de la facture), rattaché à la dépense de la facture (jamais créée par la réception). Une facture sans dépense, saisie par `saisirFacture.js`, crée une dépense payée hors audit avec sa pièce attendue (`dejaPayee`, admin seulement). L'inventaire (`GET /api/admin/inventory/global?famille=`) liste tous les produits, même à 0. L'ancien formulaire des bons (`items`) reste accepté sur tout bon (choix du porteur).
- Règles de composition : simples libellés (D-14), multiplicateurs facultatifs ; les quantités par pack du catalogue font foi.
- Idées de repas (section `repas`) : rédigées par les gestionnaires et le nutritionniste, publiées par l'admin seulement, avec la mention « Ces conseils ne remplacent pas l'avis d'un professionnel de santé. »
- Simulateurs : paramètres enregistrés côté serveur, vides par défaut ; méthode du référentiel (matières × coefficient, ÷ (1 − marge cible)).
- Nutrition : aucune donnée de santé ni conviction religieuse sans autorisation préalable de l'APDP (Code du numérique, art. 394).
- Écrans admin : vérifier l'affichage à 375 px ; la Logistique est conçue d'abord pour le téléphone. Accessibilité : `v-defilable="'Nom'"` sur une zone qui défile sans élément cliquable (admin ; attributs statiques sur l'accueil, pour la vitesse), `v-onglets` sur une barre `role="tablist"` ; couleurs de texte de la charte (`text-gris`, jamais `text-gray-*`) ; un h1 par page ; titre d'onglet dans `TITRES` du routeur.
- Comptes : adresse e-mail toujours en minuscules (`normaliserEmail`, schéma `User` ; les anciens comptes restent trouvables jusqu'à la migration, qui signale les doublons sans les fusionner) ; mot de passe de 5 caractères minimum à l'inscription et à la réinitialisation (`MOT_DE_PASSE_MIN`, même valeur dans les formulaires), sans contrôle de longueur à la connexion.
- Navigation et session : la déconnexion passe par `useDeconnexion` (retour à l'accueil, cache vidé, session gardée si le serveur ne confirme pas). Toute page affichée sans le menu du site (`hideNavigation`) propose `LienAccueil`. Une page protégée renvoie vers `/login?redirect=…` (et `&session=expiree` sur un 401) ; seuls les chemins internes sont acceptés comme `redirect`.
- Session : `GET /api/auth/session` (toujours 200, `user: null` pour un visiteur) sert à l'affichage (« Mon espace » dans le menu du site). Cookie et jeton passent par `back/src/services/sessionService.js` : 1 jour pour les clients et l'admin principal (`User.adminPrincipal`), 1 h glissante pour le reste de l'équipe, avec déconnexion côté navigateur après 1 h sans activité (`useDeconnexionInactivite`, avertissement 2 min avant, `/login?session=inactivite`).
